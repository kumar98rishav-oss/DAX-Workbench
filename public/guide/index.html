The idea in one line

Three planes: the agent works, the cockpit governs, the engine decides.

Architecture

Where the data comes from, and who talks to whom

Everything is local — no cloud, no Azure, no account. The bridge (.NET) speaks the engine's protocol; the host (Node) owns pipeline state; the agent and the UI both read and write the same state, so what you see in the cockpit is exactly what the agent sees over MCP.

Stage-by-stage internals

What runs, what's checked, and what you can customize — every stage

Each stage has four facets: RUNS (the skills and tools doing the work) · READS / WRITES (the files involved) · VERIFIES (the validation built into the stage) · CUSTOMIZE (what you can edit to change behavior). This is the layer that makes it engineering, not prompting.

00 Bootstrap

RunsThe pipeline's own step — the agent + pipeline_status / pipeline_get_plan MCP tools to read the cockpit's Source and plan.
Reads / writesReads project-spec.md (the WHAT: audience, KPIs, pages, constraints) and CLAUDE.md (house rules: workflow, standards, no-gos) from the project folder; reads the Source path set in the cockpit. Writes the first assumption-log entries.
VerifiesEnvironment gate: bridge :5177 alive, pipeline host :5178 alive, required skills present in the registry, source path exists and is readable, spec discovered (or "no spec — proceeding with defaults" declared honestly).
CustomizeThe spec template (project-spec-template.md in the registry), CLAUDE.md house rules, and the stage's own note via the cockpit pencil.

01 Profile

Runsprofile-data — the agent writes and executes a profiler script over the raw files (columns, types, grain, cardinality).
Reads / writesReads every source file. Writes control totals into the cockpit as reconciliation baselines (via pipeline_report) — the single most important write in the whole pipeline — plus profile findings to the run notes.
VerifiesType inference per column · grain uniqueness (e.g. timesheet (Date, Consultant, Project) must be unique) · key cardinality · referential integrity (0 orphans; in the RLS delta this validated that UserAccess.csv's Region/Practice values exist in the dims — a typo here would have silently produced an empty report for a manager) · control totals captured from raw data become the ground truth every later gate reconciles against.
CustomizeAdd checks to the profiling checklist; decide which totals become baselines; set per-baseline tolerance.

02 Classify & Design

Runsclassify-data — fact-vs-dimension classification, relationship inference, date-table strategy, measure candidates.
Reads / writesReads the profile + spec sections 2–4. Writes the star-schema design into the stage log — reviewable before any object exists.
VerifiesStar-schema rules: every fact key resolves to exactly one dimension · no snowflake chains · single-column keys · one marked date table with role-playing handled via inactive relationships (e.g. InvoiceDate active, DueDate inactive).
CustomizeNaming conventions and modeling standards (in CLAUDE.md or the spec) — the design must comply with what you wrote there.

03 Shape (ETL)

RunsBuilt-in ETL planning — cleaning expressed as Power Query M steps, never manual edits.
Reads / writesReads spec §2 quirks (bench members, sentinel codes). Writes the typing plan; data fixes are documented (see DATA_CLEANING_LOG.md — provenance for every byte changed).
VerifiesTyping plan derived from the profile, not guessed (IDs → Text so no leading-zero loss; dates → Date; flags → Int64) · post-clean referential integrity re-checked = 0 orphans · reconciliation totals unchanged by cleaning.
CustomizeCleaning rules and quirk handling declared in spec §2 — the stage implements what the spec declares.

04 Model

Runssemantic-model-authoring (the plugin skill: HOW to model well) + powerbi-modeling-mcp (Microsoft's MCP — the hands: TOM operations for tables, relationships, calc groups, field parameters, roles). In the RLS delta run the agent edited the TMDL text directly — same artifact, different hands.
Reads / writesReads the stage-2 design + spec §4/§7. Writes *.SemanticModel/definition/*.tmdl — tables with M partitions, relationships, the calculation group, RLS roles — and assembles the openable PBIP wrapper.
VerifiesThe model must compile under TOM (bad DAX or a broken reference fails the create call loudly) · standards enforced: hidden FKs, discourageImplicitMeasures, marked date table, sort-by columns, format strings on everything · PBIP assembly validated against a known-good wrapper structure.
CustomizeModeling standards in the skill/CLAUDE.md ("always a calc group for time intelligence"); RLS design in spec §7/§8b; TMDL is text — you can hand-edit any of it and Git will show the diff.

05 Measures

Runsdax-workbench — my own MCP server: pbi_validate_measure, pbi_run_dax, pbi_benchmark_dax, pbi_write_measure.
Reads / writesReads measure candidates + spec §4. Writes the measure catalogue into the model (37 measures in run 1: time intelligence, AR aging, utilization, RANKX, what-if, dynamic titles).
VerifiesThree layers, in order: (1) static schema grounding — every table/column/measure reference must exist in the live model, which makes hallucinated names structurally impossible to write · (2) engine evaluation — the measure is run on real data and reconciled against the Profile baselines · (3) performance — benchmark_dax times cold-cache before any speed claim (full catalogue: 51 ms). Style rules from the skill: DIVIDE never "/", VAR for readability, measures reference measures.
CustomizeYour domain's measure library (spec §4 or a domain skill); format and display-folder conventions; which measures join the baseline set.

06 Plan

Runspowerbi-report-planning plugin skill — pages, visuals, interactions, drill-throughs, tooltips.
Reads / writesReads spec §3 (business questions) + §5 (page structure). Writes the page-by-page plan with an insight-per-page statement.
VerifiesField-refs check: every field a planned visual binds must exist in the validated model — dead bindings are caught on paper, before a single visual is authored.
CustomizePage archetypes and interaction patterns (drill-through targets, tooltip pages) in the spec.

07 Style

Runshouse-report-design (my skill: swappable style packs — default nexus — each a theme.json + design guidance) + house-report-build (theme schema rules).
Reads / writesReads the pack's style.md + theme.json. Writes/applies the validated theme — one file styles every visual.
VerifiesThe theme is pre-validated against Power BI's importer: only standard top-level keys (a non-standard key fails the import — a bug we hit once and encoded), no render-breaking style properties, every fontSize ≥ 8, semantic colors always paired with labels.
CustomizeThe most customizable point in the pipeline: a client brand = one new style-pack folder (theme.json + notes). Swap the default pack by name.

08 Author

Runspowerbi-report-authoring (plugin) + house-report-build — my skill carrying references/pbir-schema.md (visual types → query roles), references/error-playbook.md (every render bug → fix), references/conditional-formatting.md (FillRule patterns) and generator scripts.
Reads / writesReads the plan + design system. Writes the report as code: pages/*/visuals/*/visual.json (~50 visuals in run 1, incl. matrix, quadrant scatter, gauge, drill-through page, tooltip page, slicers, conditional color).
VerifiesEvery visual.json parses and matches the visual-container schema · playbook enforcement makes known bugs unrepeatable: matrix (pivotTable) not tableEx, container objects inside visual, FillRule inner nodes as bare literals — each rule is a render error we paid for exactly once · a render-confirm checkpoint before scaling from one page to six.
CustomizeEdit the skill's SKILL.md rules; add visual archetypes; extend the playbook when a new visual type is learned (read one known-good example, encode it).

09 Integration QA

Runsdax-workbench + the host's own verifying gate (POST /pipeline/verify) — note who runs this one: the host, not the agent.
Reads / writesReads the stored baselines. Writes the gate result + per-check evidence (expected vs engine, with deltas) into the stage log.
VerifiesThe independent check: the host EVALUATEs the baseline measures through the bridge on the live engine and compares within 0.1% tolerance — the gate goes green from the engine's numbers, never from the agent's claim · visual-error scan across pages · RLS persona matrix (in the delta run: Admin baselines unchanged to the penny; the three regions partition to exactly 100% — Europe $28.02M + India $20.17M + NA $14.68M = $62.87M; unknown email → blank) · performance timing.
CustomizeAdd checks (accessibility, extra personas); tighten tolerance; require sign-off (default on).

The gate that catches a lying agent

The host calls the bridge: POST /dax → EVALUATE ROW("m0",[Revenue], …) — then compares within 0.1% tolerance.

Why this matters

An AI can produce a plausible wrong number. This gate makes that impossible to ship: if the model's measures don't reconcile with the source data, the pipeline stops itself — with the exact measure and delta on screen.

What the agent can't do

The MCP control tools are deliberately limited: the agent can run and pause, but it cannot approve a sign-off or release a breakpoint. Only a human in the cockpit can. Governance by construction, not by prompt.

The compounding loop

Run a delivery → hit a problem → fix it → encode the fix as a skill rule → register it in the folder → the next run inherits it automatically. This is how the first build's three debugging sessions became the second build's zero. The tool doesn't just automate work — it accumulates judgment.

first run: 3 in-process debugs second run: 0 — the skill absorbed them
Version control · why Git is a pillar, not a checkbox

Git works here because the deliverable is text

A .pbix is a binary blob — Git can store it but can't diff, review, or merge it. This pipeline's output is TMDL + PBIR + markdown: pure text. That single design choice is what unlocks every practice below — it turns BI delivery into software delivery.

History & rollback

Every run commits. A bad change? git revert restores the previous model — including the previous security model — in seconds, with the reversal itself audited.

undo for governance, not just code

Review at the gate

The breakpoint pairs with git diff: in the RLS run, the reviewer approved a readable diff of the role's DAX filter — a security change reviewed as text before it could ship. That is change management most BI teams don't have.

the diff is the approval artifact

Audit & blame

"Who changed this measure, when, and why?" — git log + git blame answer per line of TMDL. Paired with the cockpit's gate history, every number has a paper trail.

compliance-grade traceability

Branches & PRs

A change request = a branch. The delta pipeline runs on the branch; the PR shows exactly the 3 files the RLS change touched; merge = deploy-ready. Two people can work two CRs without collisions.

BI change requests as pull requests

Distributing the process

The skills (.claude/skills/) and pipeline templates are files too — commit them to a shared repo and the whole team inherits the delivery standard, reviewable and versioned like everything else.

process as code, shared via Git

CI hook

The verify endpoint is plain HTTP. Wire it into a PR pipeline and a model change cannot merge unless the baselines still reconcile — regression testing for numbers.

roadmap: one YAML file away

Interview Q&A · likely questions, strong answers

What they'll ask — and how to answer

Isn't this just a wrapper around Claude prompts?
No — three things exist here that no prompt can provide: hands (an MCP server that validates and executes DAX on the live engine), independent verification (the host re-computes baselines itself — the agent can't self-certify), and persistence (skills, templates, baselines, history — all files). Remove the prompts entirely and the architecture still stands; remove the architecture and you're back to pasting DAX and hoping.
How do you stop the AI hallucinating column or measure names?
Structurally, not by asking nicely. pbi_validate_measure statically resolves every table, column and measure reference against the live model schema before the expression can be written — an invented name fails validation and is never deployed. Then the expression is evaluated on the engine and reconciled against baselines. In run 1, 37 of 37 measures passed on the first engine run.
What happens when the AI produces a plausible but wrong number?
That's exactly what the verifying gate exists for. Ground truth is captured at Profile from the raw files, before any modeling. At the Measures and QA gates the host — not the agent — EVALUATEs those baselines on the engine and compares within 0.1%. I can demo it: tamper a baseline and the gate goes RED with the measure and delta on screen. A plausible-but-wrong number cannot reach Package.
You let an AI touch row-level security? How is that safe?
Because the pipeline treats security as its most-governed change, not its least. The RLS change ran as a delta: the new access table was domain-validated at Profile; the role change was written as TMDL text and held at a human breakpoint where I reviewed the actual diff; QA then proved Admin baselines were unchanged to the penny, the region personas partition to exactly 100%, and an unknown email sees nothing — deny by default. And the best part: profiling caught that the literal spec would have collapsed one practice's view to $1.25M, so the design was corrected before it shipped.
Why MCP instead of a Python script calling APIs?
MCP makes the tools agent-native and reusable: typed schemas, discoverability, and the same 19 tools work from Claude Code, Claude Desktop, or any MCP client — no glue code per environment. It also enforces the trust boundary cleanly: the agent gets validate/run/benchmark, but gate-release and sign-off deliberately have no MCP tool — those are cockpit-only, human-only.
What did the AI actually get wrong? (the honesty test)
Run 1 hit three real issues: an offline calculated date table that couldn't bind relationships (rebuilt as an M table), a report visual type that throws on render (switched to matrix), and a conditional-format expression shape that crashed on interaction (fixed to bare literals). Each was fixed in-process and encoded into the skill — run 2 hit zero. I also commissioned a critical review of my own tool; it said "it tracks, it doesn't build" — so I built verifying gates and cut the agent's status payload by 96% the next day. I'd rather show you the fix-loop than pretend there were no bugs.
How does this scale to a team?
Everything that matters is a file: skills, templates, specs, the deliverable itself. Commit the registry to a shared repo and every analyst inherits the same pipeline, standards and error playbook; change requests become branches; the verify endpoint becomes a CI check on PRs. The cockpit means a lead can supervise a delivery without reading prompts. What's genuinely single-user today is the local host state — that's on my production-hardening list, with a clear path (shared host + the token-auth pattern the bridge already uses).
Where does the data go?
Nowhere. The entire platform is local-first: the bridge binds to loopback, the host binds to loopback, there's no account, no telemetry, no cloud dependency. The AI reads schema and query results through local MCP calls. That posture was a design goal — it's what makes the tool usable on client data.
How do you handle performance on large models?
Measured, never asserted: benchmark_dax clears the cache and does a warm-up pass so timings are honest cold-cache numbers; the storage analyzer (same library DAX Studio uses) finds the expensive columns; the optimizer proves rewrites with before/after timings and refuses to claim a win when the delta is inside noise. The demo model's full 37-measure catalogue evaluates in 51 ms cold — small data, but the discipline is what scales.
Why is the output PBIP and not a .pbix?
PBIP stores the model as TMDL and the report as PBIR — text. That's what makes Git meaningful: diffs, reviews, blame, rollback, CI. A .pbix is a binary blob you can only version, not review. PBIP is also Microsoft's strategic direction for pro BI development, and it round-trips into Desktop and the Service.
If Microsoft ships Copilot for all of this, why does your tool matter?
Copilot is a worker; this is the operating model around any worker. The pipeline, verifying gates, human sign-offs, skills registry and audit trail are agent-agnostic — the MCP layer means I could swap the agent tomorrow. If anything, better AI workers make the governance layer more valuable, because more work happens without a human writing it.
What would you build next?
Three things, in order: a headless engine step so scratch-to-Git needs zero manual opens; the CI verify hook so model PRs can't merge if baselines break; and a deployment skill wrapping report-management so Package can push to a Fabric workspace behind a final sign-off. All three are content or thin glue — the architecture already has the seams for them.

Honest engineering · production readiness

What's solid, what needs fine-tuning, and how

"Production-ready" is a claim that should come with a punch list. Here's mine — the green rows are load-bearing today; the amber rows have a named gap and a concrete fix.

Engine verification loopSOLIDSchema grounding + engine evaluation + host-run gates, proven across 3 runs. One dependency: a live model must be open in Desktop for the engine to answer.
Governance & auditSOLIDBreakpoints, human-only sign-offs, on-fail branches, per-gate evidence, 20-run history, generated docs. The agent's control tools are run/pause only — by design.
Skills & registrySOLIDFolder-based, Git-shareable, live in the cockpit. Growth is content (more packs, more domains), not code.
Local security postureSOLIDLoopback-only, no account, no telemetry; RLS deny-by-default pattern shipped and persona-tested.
Headless verificationTUNEToday a human opens the pbip so the engine loads data. Fix: scripted Desktop launch + wait-for-port at the gate, or point the bridge at a Fabric XMLA endpoint — then scratch → verified → Git is one shot.
Team / multi-userTUNEHost state is per-machine. Fix: run the host as a small shared service with bearer-token auth (the bridge already implements exactly this pattern for remote pairing) — the UI and MCP layers don't change.
Visual-type coverageTUNEThe PBIR playbook covers the 12 core types used so far. Fix per new type: read one known-good example, encode its query roles + quirks into the skill — the same learn-from-a-template method that built the current playbook.
DistributionTUNESingle self-contained exe with update-check, but unsigned (SmartScreen prompt). Fix: code-signing certificate; optionally an installer that registers the External Tool without the UAC step.
CI/CD integrationTUNEThe verify endpoint is plain HTTP and already scriptable. Fix: a GitHub Action / Azure DevOps task that runs it on PRs touching the SemanticModel — RED blocks the merge. Roughly a YAML file of work.

The pattern across every amber row: the architecture already has the seam — each fix is thin glue or content, not a redesign. That's what "almost production-ready" means concretely.
