1 Data ingestion

How data enters the tool

There are four paths. The right one depends on whether Power BI Desktop is open, and whether you have a real report file. Each path ends up in the same in-memory SemanticModel object.

Path 1 — File import (Excel / CSV / Parquet)

You drag or pick a file. The browser's File API reads it locally — no upload, no server. The file goes through a chain of parsers:

File pick
browser File API
Parser
xlsx / csv / parquet
inferSchema
detect types, roles
buildModel
detect relationships
store
datasets + model
  • inferSchema() scans up to 10,000 rows to detect data types (int, decimal, date, string, boolean), cardinality, and column roles (key, dimension, measure candidate, date).
  • buildModel() runs a fuzzy name-matching + cardinality heuristic across all imported tables to detect one-to-many relationships. A column named ProductID in a fact table matching a primary key ProductID in a dimension table becomes a relationship automatically.
  • A Preview dialog shows the user what will be imported before it commits to the store.
Path 2 — Open PBIX / PBIP project

PBIX and PBIP are Power BI's own file formats. The tool opens them without Power BI Desktop — purely in the browser.

PBIX (binary zip)

A .pbix is a zip file containing a DataModel binary (proprietary). The parser reads the TMDL portion (Tabular Model Definition Language) to extract table names, column names, data types, measures, and relationships. Actual row data is not included — the tool works with schema only, showing placeholder values. The user sees a warning: "Best-effort — no data."

PBIP (folder tree)

A .pbip folder is the modern Power BI project format (plain text, git-friendly). It contains a definition/ folder with .tmdl files — one per table. The parser walks the folder tree, reads each TMDL file, and builds the full model.

PBIP also has a separate report layer (visual bindings). A special "Scan Report" flow reads the report files to find which measures are actually used in visuals — this powers the Cleanup tab's "unused measures" detection.

Path 3 — Live Desktop sync (the flagship path)

This is the path that makes everything real. Power BI Desktop runs a private Analysis Services (SSAS) instance for each open report. The bridge finds it and talks to it directly.

1

Discover

GET /discover — the bridge scans all running processes on the machine for msmdsrv.exe instances (the Analysis Services process that Desktop spawns). For each one it finds, it reads the TCP port from the process's command line or a port file. Returns a list of {port, database} pairs.

2

Read the model

GET /model?port=N — the bridge connects to that SSAS port using TOM (Tabular Object Model) — Microsoft's official .NET library for interacting with Analysis Services. It reads every table, column (name + data type), measure (name + DAX expression + format string), and relationship. Returns this as JSON.

3

Map to SemanticModel

The frontend receives the JSON and maps it into the in-memory SemanticModel. Column data types are normalised (Desktop uses names like Int64, String — mapped to the tool's simpler 'integer', 'string' etc).

4

Keep polling

The home screen polls /discover every 4 seconds to keep the connection status badge live. There is no WebSocket — plain HTTP polling.

Why ADOMD too? TOM is used for model reads and writes (measure CRUD). ADOMD (Analysis Services Data Mining Objects) is used to run DAX queries against the real data — the KPI board and the Matrix/Table views all use ADOMD via the /dax and /time endpoints.
Path 4 — Remote bridge (another machine)

A remote colleague can run the bridge with --remote and share their model over the network. The bridge then listens on 0.0.0.0 instead of loopback. A pairing token (32-character hex, randomly generated) is shown as a QR / text pair. The user enters the token + URL in the "Remote Bridge" dialog. Subsequent API calls include Authorization: Bearer <token>. The token is persisted to localStorage so reconnect is seamless.

2 The bridge

The bridge: a self-contained universe

The bridge is a C# .NET 8 self-contained Windows executable. It is the product's most important file — it is the only process that can touch the Analysis Services engine.

What it actually is
Runtime
.NET 8, self-contained — .NET does not need to be installed on the user's machine. The runtime is bundled inside the exe.
UI embedding
The entire React frontend (dist/) is embedded as EmbeddedResource in the .csproj and served by ManifestEmbeddedFileProvider. The exe IS the web server.
Single-instance guard
A named Mutex("Local\dax-workbench-bridge") ensures only one bridge runs. A second launch opens the browser instead.
System tray
WinForms system tray icon. Right-click menu: Open Studio, Switch to Remote, Register External Tool, Exit.
Listen address
127.0.0.1:5177 in local mode (only this machine). 0.0.0.0:5177 in remote mode (network-reachable).
External Tool
Power BI Desktop's External Tools ribbon reads pbitool.json. The bridge registers it: when clicked, Desktop calls the bridge with --launch "server" "database".

HTTP API endpoints

All endpoints answer on http://127.0.0.1:5177. CORS allows localhost origins and the Render deployment.

Method Path What it does Backed by
GET /health Returns {status:"ok", machine:"hostname"}. Used to check if the bridge is alive. No auth required. Hard-coded response
GET /discover Finds all running Power BI Desktop instances. Returns [{port, database}]. Port = the SSAS TCP port. Process scan + TOM
GET /model?port=N Reads the full TOM — all tables, columns, measures, relationships. Returns as JSON matching DesktopModel interface. Microsoft TOM library
POST /dax Executes a DAX query (EVALUATE expression). Returns {columns, rows, rowCount}. Powers KPI board live values. ADOMD query
POST /preview Evaluates a scalar DAX expression. Used in the DAX tab live preview pane. ADOMD EVALUATE
POST /time Benchmarks a DAX query — runs N times (default 3), clears the engine cache before each run, returns min/median/all timings. Used by DAX Optimizer. ADOMD + cache clear
POST /measure Creates or updates a single measure in the live model. Body: {table, name, dax, formatString, displayFolder}. Writes via TOM + Model.SaveChanges(). TOM write
POST /table Creates a calculated table (e.g. a generated Date table). Optionally marks it as the model's date table and relates it to a fact column. TOM write
POST /delete Deletes measures from the live model. All-or-nothing: snapshots all targets first, then commits one transaction. Snapshot returned for rollback. TOM write
POST /nim Proxies AI generation requests to NVIDIA's API. The API key travels server-side only — never appears in browser network logs. 120 second timeout. HttpClient → NVIDIA

Security model

Who is allowed to call the bridge?
Loopback callers (localhost, 127.0.0.1) — always allowed, no token required. This covers the dev server, the embedded UI, and local Tauri builds.
Allowlisted origins — https://dax-workbench.onrender.com is hardcoded. Additional origins can be added via the PBI_BRIDGE_ORIGINS environment variable.
Remote callers — mandatory Bearer token. Generated with RandomNumberGenerator.GetBytes(16) (cryptographically secure). CORS is a browser guard only; the token is the real gate for non-browser clients.
CORS only gates browsers — curl can still reach a remote bridge without it. The token is what actually protects the model.
Chrome's Private Network Access (PNA) preflight

Chrome enforces "Private Network Access" — a page served over HTTPS cannot reach 127.0.0.1 without an explicit opt-in from the server. The bridge adds Access-Control-Allow-Private-Network: true to any response that has the Access-Control-Request-Private-Network request header. This is why the Render-hosted version can still talk to a local bridge.

3 Frontend

The React application

A single-page application built with Vite + React + TypeScript. The entire app lives at one URL — routing is handled by toggling a view state variable, not the browser router.

State management: Zustand

A single Zustand store (src/app/store.ts) holds all application state. There is no Redux, no Context tree of providers. Any component that needs state calls useApp(selector). State is never passed as props down the tree.

model
SemanticModel
The in-memory mirror of the Power BI model. Tables, columns, measures, relationships. Rebuilt on every sync.
datasets
DatasetData[]
Actual row data from imported files. Parallel array to model.tables — indexed by table ID. Kept in memory, never persisted.
desktop
DesktopStatus
{bridge, connected, database, port, machine}. Polled every 4 seconds on the home screen.
mode
'kpi'|'data'|'model'|'cleanup'|'dax'
Which studio tab is active. Switching mode auto-collapses the left/right panels (except KPI where they stay open).
nimApiKey
string
The NVIDIA NIM key. Persisted to localStorage['pbistudio.nimApiKey'] — lives across refreshes.
kpiOverrides
Record<number, string|null>
User's manual slot assignments on the KPI board. Overrides the auto-fill. Persisted to localStorage.

The five studio modes

KPI
12-card live board showing real measure values, queried from the SSAS engine via /dax. Also includes Matrix (pivot) and Table (flat) views. All three run live DAX queries when connected.
Data
Tabular browser for the imported datasets. Shows real rows from files. Not connected to the live engine — this is for exploring your imported data, not Desktop's data.
Model
Two views: Diagram (relationship graph drawn with force-directed layout) and Relationships (a plain list, exactly like Power BI's "Manage Relationships" dialog). Relationship arrows show cardinality symbols (✱ = many, 1 = one) and cross-filter direction (◄ or ◄►).
Cleanup
Audits the model for unused measures. Measures are compared against a report scan (visual bindings) and the known set of references (DAX dependencies). Staged deletions are queued first — nothing touches the real model until "Deploy" is clicked. Undo/redo of the staging queue is unlimited.
DAX
The main workspace. Measure tree on the left, editor + live preview on the right, reference panel (Functions / All DAX / Optimizer) on the far right. AI Generate, Architect, Factory, and Optimizer all surface here.
4 Domain model

The in-memory data model

Everything the tool knows about your Power BI model lives in one TypeScript object called SemanticModel. Think of it as a lightweight TOM mirror. 

interface SemanticModel {
  tables:        Table[]
  relationships: Relationship[]
}

interface Table {
  id:       string        // stable UUID — survives renames
  name:     string
  isHidden: boolean
  columns:  Column[]
  measures: Measure[]
}

interface Column {
  id:            string
  name:          string
  dataType:      'string'|'integer'|'decimal'|'boolean'|'date'|'datetime'
  role:          'key'|'dimension'|'measure'|'measureCandidate'|'date'|'time'
  isHidden:      boolean
  distinctCount: number | undefined
  formatString:  string | undefined
}

interface Measure {
  id:              string
  name:            string
  expression:      string        // the DAX, without "Name = " prefix
  formatString:    string | undefined
  displayFolder:   string | undefined
  isAutoGenerated: boolean       // true = created by the Measure Factory
}

interface Relationship {
  id:              string
  fromTable:       string        // table IDs, not names
  fromColumn:      string        // column IDs, not names
  toTable:         string
  toColumn:        string
  fromCardinality: 'one'|'many'
  toCardinality:   'one'|'many'
  crossFilter:     'single'|'both'
  isActive:        boolean
}
Relationships store IDs, not names. When displaying a relationship in the UI (e.g. the Relationships list in Model tab), the code builds a Map<id, Table> and resolves names at render time. This means renaming a table never breaks a relationship.
5 AI pipeline

How AI Generate works, end to end

You type "total sales last year, excluding returns". Three seconds later you have working DAX. Here is every step in between.

1

User types a prompt

Free-form English. No syntax needed. The user can optionally set a target table (where the new measure should live).

2

Schema serialisation

modelToSchemaPrompt(model) converts the live SemanticModel into a compact pseudo-SQL DDL string — roughly 3–5 tokens per column. Hidden tables and hidden columns are excluded. Columns are capped at 30 per table. Existing measures are appended as MEASURE pseudo-statements (capped at 50) so the AI can see what already exists and build on it.

-- Example output for a Sales table
CREATE TABLE Sales (
  'Order Date'  DATE,
  'Product ID'  INT,
  Amount        DECIMAL,
  Quantity      INT,
  'Ship Status' VARCHAR
);

-- Existing measures (reference only — do not redefine them)
MEASURE Sales[Total Sales] = SUM(Sales[Amount])
3

System prompt construction

The schema DDL is injected into a strict system prompt. The rules force the model to:

  • Use only exact table/column names from the schema — never invent or abbreviate
  • Return only the DAX expression — no markdown, no prefix
  • Reply with CANNOT_GENERATE: <reason> if the prompt can't be answered from the schema
  • Prefer CALCULATE + FILTER over nested IFs
  • Use time-intelligence functions for time calculations
4

Call via bridge proxy

The React app posts to http://127.0.0.1:5177/nim (or the bridge origin if served from the bridge). The bridge forwards the request to https://integrate.api.nvidia.com/v1/chat/completions using the stored API key. This means:

  • The browser never calls an external host — no CORS issue
  • The API key never appears in browser network logs
  • The bridge uses a 120-second timeout (DeepSeek R1 can be slow)
Model: deepseek-ai/deepseek-v4-flash via NVIDIA NIM free tier. 40 requests/minute, 1M token context window, no daily token cap. Temperature is locked at 0.1 for consistency.
5

Response cleaning

DeepSeek V4 Flash (like R1) sometimes wraps its reasoning in <think>…</think> blocks. These are stripped with a regex before the DAX is shown. If the response starts with CANNOT_GENERATE:, the error message is extracted and shown to the user instead.

6

Hallucination guard

findHallucinatedNames(dax, model) parses the returned DAX expression using the dependency parser (parseDependencies) to extract all table/column references. Each reference is checked against the known schema. Any reference that doesn't match an actual column is flagged as hallucinated and shown as a warning banner in the UI. The user can still accept the DAX, but they're warned.

// Hallucination check — simplified
const allColKeys = new Set(
  model.tables.flatMap(t =>
    t.columns.map(c => `${t.name.toLowerCase()}[${c.name.toLowerCase()}]`)
  )
)
return deps.columns
  .filter(col => !allColKeys.has(`${col.table.toLowerCase()}[${col.column.toLowerCase()}]`))
  .map(col => `${col.table}[${col.column}]`)
✓

Result + auto-naming

A measure name is suggested from the prompt by stripping stop words, taking the first 4 content words, and title-casing them. The user can edit both the name and the DAX expression before accepting. Accepting it calls /measure on the bridge which writes it directly to the live Power BI model.

DAX Architect — the deterministic engine

The Architect is a separate, fully deterministic engine that generates DAX without any AI. It is used when you want ranked pattern suggestions — not one answer, but a scored list of approaches (SUMX vs SUM, CALCULATE with filter vs context transition, etc).

The Architect runs entirely in the browser — no API call needed. It reads the SemanticModel, parses the natural-language prompt with a filter-column injection step (it rewrites "where status = delivered" into a proper column reference), then runs a scoring engine across a library of DAX patterns to produce ranked suggestions.
6 Features

Feature internals

KPI Board — live query loop

The KPI board shows 12 cards. Each card displays the live scalar value of a measure, queried from the real SSAS engine.

1

Slot assignment

Measures auto-fill newest-first (hand-written measures before auto-generated ones). The user can manually pin any measure to any slot via the dropdown on each card. Overrides are stored in kpiOverrides (localStorage-persisted).

2

Batch query

buildKpiBoardQuery() builds a single DEFINE … EVALUATE ROW(…) DAX query that fetches all 12 measure values in one round-trip. A 400ms debounce prevents flooding the bridge when measures change rapidly.

3

Local fallback

When not connected, evaluateDax() runs the measure expression through an in-browser interpreter (query-engine.ts) against the imported dataset rows. Sample values — not accurate for complex DAX, but useful for design time.

Measure Factory — combinatorial generation

You pick a numeric column. The Factory generates the full analytical suite for it in one click.

What it generates
Total (SUM)
Year to Date (DATESYTD)
Quarter to Date
Same Period Last Year
Year-over-Year %
Month-over-Month %
3-month Moving Average
Running Total
Rank (all periods)

All generated measures have isAutoGenerated: true — the KPI board auto-fills them after user-written measures. The date intelligence functions require a proper date table in the model.

Cleanup — staged, safe deletion

Cleanup detects unused measures and lets you delete them from the live model. But "delete" is an engine operation that can't be undone — so the system uses a two-phase approach.

Phase 1 — Staging: Measures are added to a cleanupStaged list in the store. Nothing touches Desktop. Undo/redo is unlimited and instant because it only operates on the staging list in memory.
Phase 2 — Deploy: POST /delete is called with all staged items. The bridge snapshots each measure (table, name, DAX, formatString, description) before removing any. It then commits one transaction. If the commit fails, the snapshot is still returned — you can restore. If it succeeds, the snapshot is kept in the store as a rollback option for the session.

Unused detection logic: A measure is "potentially unused" if it appears in no other measure's DAX expression and was not found in any visual binding in the scanned report files. Both conditions must be met — a measure used only in other measures is still counted as in-use.

DAX Optimizer — before vs. after timing

The Optimizer suggests rewritten DAX (via templates or AI) and then actually benchmarks both versions. POST /time runs a DAX expression N times (default 3 runs), clearing the engine's formula engine cache before each run with a special clear-cache DAX command. It returns min, median, and all individual timings, plus a flag cold: false if the cache couldn't be cleared (meaning the numbers are warm-cache only).

Date Table Builder

Generates a calculated date table using Power BI's CALENDARAUTO() or a custom range, with optional fiscal year offset. The DAX for the table is generated client-side (no AI needed — it's a deterministic formula). POST /table deploys it to the live model, and the bridge optionally marks it as the model's official date table and creates a relationship to the specified fact column. After deploy, the store calls syncFromDesktop() to refresh the model so the new table appears immediately in the Data and Model tabs.

8 Build pipeline

From source to shipped exe

There are two build targets: the hosted web app (Render, automatic) and the External Tool exe (manual, one command).

Target 1 — Render (hosted site)

Push to main on GitHub → Render detects the push → runs npm run build → deploys dist/ as a static site. Zero manual steps. Takes ~2 minutes.

Target 2 — External Tool exe (build-full.cmd)

build-full.cmd — step by step
npm run build
Vite compiles → dist/
robocopy /MIR
dist/ → bridge/wwwroot
dotnet publish
wwwroot embedded → single exe
publish/
pbi-desktop-bridge.exe ready
dotnet path: The system dotnet is at C:\Program Files (x86)\dotnet\dotnet.exe — not in PATH. Always use the full path, or run build-full.cmd which sets it correctly. 
# Kill the running bridge first (it locks the exe file)
taskkill /F /IM pbi-desktop-bridge.exe

# Then rebuild everything in one command:
tools\pbi-desktop-bridge\build-full.cmd
Why does the External Tool need a rebuild but Render doesn't?

Render serves the React app as a static site — it rebuilds from source on every push and serves dist/ directly. The External Tool exe is different: the frontend is embedded inside the exe as binary resources using ManifestEmbeddedFileProvider. When you push to GitHub, the exe on your machine doesn't change. Only running dotnet publish (after copying the new dist/ into wwwroot/) bakes the new frontend into the exe.

This is why you can see a new feature on the Render site but not in the External Tool — you have an old exe with old embedded HTML/JS. Always rebuild after UI changes you want in Desktop.
9 Publish this guide

How to put this on GitHub Pages

GitHub Pages serves static files directly from a repo branch or a /docs folder. Five steps.

1

Save this HTML file to your repo

Copy this HTML file into your DAX-Workbench repository. A good location:

docs/index.html

Or in a dedicated folder like docs/architecture/index.html.

2

Commit and push

git add docs/
git commit -m "Add architecture guide"
git push origin main
3

Enable GitHub Pages in repository settings

Go to your GitHub repo → Settings → Pages. Under "Source", choose Deploy from a branch. Set branch to main, folder to /docs. Click Save.

4

Wait ~1 minute

GitHub Actions will run a Pages deploy. You can watch it under the Actions tab. When the deploy icon turns green, your page is live.

5

Your URL

The page will be live at:

https://kumar98rishav-oss.github.io/DAX-Workbench/

If you put it in a subfolder, it'll be /DAX-Workbench/architecture/. GitHub Pages automatically serves index.html from any folder.

Tip: If your repo is private, GitHub Pages requires a paid plan. For a public repo (which yours already is — it's on GitHub), Pages is free on any plan.
Alternative: deploy with a gh-pages npm package

If you want to auto-deploy from CI rather than the /docs folder:

npm install --save-dev gh-pages

# In package.json:
"scripts": {
  "deploy:docs": "gh-pages -d docs"
}

# Then:
npm run deploy:docs

This pushes the docs/ folder to a gh-pages branch. Set GitHub Pages source to that branch instead of main /docs.
